1. Principles

  • One behavior implementation. Everything in concept §6–§11 is implemented once and used by both products. That is how §14.3 ("same output") is met without keeping two copies of the rules in sync.
  • Concrete, not pluggable. No dependency inversion for swapping technologies. Elements depend on concrete elements. An abstraction exists only where two real implementations exist today, such as the web and VST hosts.
  • Atoms. Each rule is a small pure function over plain data. Stateful elements are thin and compose those functions.
  • Musical state lives on the audio thread. Views never change musical state directly. User actions become commands, and the screen shows snapshots.
  • Two separate UIs. The web UI and the VST UI are separate programs with different features. They share only the Command/Snapshot contract and the skin artwork.

2. Layers

Each product is a stack of the same layers. The two bottom layers are shared; everything above them exists once per platform. Arrows mean "depends on".

Where does code go? If it needs a number from the concept's formulas, it goes in the core domain. If it touches audio sample data, it goes in the core engine. If it needs a file, a thread, a device or the host, it goes in the platform host. If it holds what the screen shows, receives a user action, or draws a control, it goes in the view model. If it connects the view model to the host, it goes in the presenter.

Nothing crosses between the two platform columns. The VST presenter never sees the web host, and the web view model never sees VST code. The only things both columns share are the two core layers below them.

5. Runtime model: threads and data flow

 UI thread                                                    audio thread
 ─────────                                                    ────────────
 view model ─ signal ─▶ presenter ─ Command ─▶ command channel ─▶ Engine.apply
                                                                                    │
                                                                                    ├─ Session
                                                                                    ├─ Renderer
                                                                                    ▼
 view model ◀─ set ── presenter ◀─ Snapshot ── snapshot channel ◀── Engine.fillSnapshot

 loader (background)
 ───────────────────
 file ─▶ decode ─▶ convert to output rate ─▶ SampleBuffer ── append track ──▶ audio thread
 owner frees buffer ◀── "track released" ◀── audio thread (after removal)

There are three kinds of work, kept on separate threads:

  • Audio thread. Owned by the DAW or the browser. It asks for a block of audio every few milliseconds and must never wait. The Engine, and with it the Session, lives here. Commands are applied at the start of each block, which is what makes Randomize and every live change take effect immediately.
  • UI thread. Runs the view model and the presenter. It never touches the Session. It writes commands into the command channel and reads the latest snapshot from the snapshot channel about 30 times a second.
  • Loader. Decoding a file and converting its sample rate takes too long for the audio thread, so it happens in the background. The finished SampleBuffer is handed to the audio thread ready to play. When a track is removed, the audio thread hands the buffer back so its owner can free it outside the audio thread.
ConcernVSTWeb
Audio threadThe DAW's audio callbackThe browser's audio rendering thread
Command channelLock-free queue inside the pluginMessage from the page to the audio thread
Snapshot channelLock-free buffer that always holds the latest snapshotMessage from the audio thread about 30 times a second
LoaderBackground thread in the pluginThe page's main thread, using the browser's decoder
Transport inputMIDI notes and the DAW's play state, read on the audio threadPlay/Stop commands from the presenter
Indices and ids. Track commands use list positions: append, remove at index, move from one index to another. Each track also carries a TrackId that never changes. It is used only to find the track's audio data and display name, never to address a command. Commands are applied in the order they were sent, so a sequence of index-based edits always lands on the intended rows.

Namespace bt. Functions are pure unless stated otherwise. Time in the domain is measured in beats or seconds, never in audio frames.

7.3 Tracks

using TrackId = uint32_t;

struct TrackInfo {
    TrackId id;               // identity of the audio data; never used to address commands
    double  durationSec;
    double  startPosition;    // 0..1
};

struct TrackGeometry { double startOffsetSec; int sliceCount; };

TrackGeometry computeGeometry(const TrackInfo&, double sliceSec);   // §6.3

class TrackList {                           // fixed capacity
public:
    static constexpr int kMaxTracks = 128;
    int  count() const;
    const TrackInfo& at(int index) const;
    std::optional<int> indexOf(TrackId) const;

    bool append(const TrackInfo&);           // §4: adds at the end
    bool removeAt(int index);                // later tracks shift up
    bool move(int from, int to);             // track at 'from' ends up at 'to'; the ones between shift by one
    bool setStartPosition(int index, double);
};
move only reorders the track list. It does not call into Sequence, and the sequence is not changed. A slot keeps its stored index, so after a move it plays whichever track is now at that index. Remap is only for a change in the number of tracks (§8.3).

7.6 Session

The only stateful domain element. Each method implements one control from concept §5 or one row of §10.

class Session {
public:
    explicit Session(uint64_t seed);

    // transport (§5)
    void play();                  // t = 0; generate if no sequence. Also used for a new note while playing.
    void stop();                  // stop, t = 0, keep sequence
    void randomize();             // §9: immediate, keeps t; does nothing with 0 tracks

    // parameters (§10)
    void setBpm(double);
    void setLoopSize(int);        // crop / extend / clamp slice and regenerate
    void setSliceSize(SliceSize); // regenerate
    void setRandomizeEvery(int);  // stored only; used by AutoRandomizer
    void setPlaybackMode(PlaybackMode);  // stored only; used by NoteTransport

    // tracks (§4)
    void appendTrack(const TrackInfo&);   // generates if playing and no sequence (§13)
    void removeTrackAt(int index);
    void moveTrack(int from, int to);
    void setStartPosition(int index, double);

    // presets (§11); also used for the DAW project
    void applyPreset(const PresetData&);  // discard sequence; regenerate if playing
    PresetData presetData() const;        // current settings + start positions

    // playhead
    int advance(double elapsedBeats);     // see below

    // queries
    bool  isPlaying() const;
    double tBeats() const;
    const Settings&  settings() const;
    const Timing&    timing() const;
    const TrackList& tracks() const;
    const Sequence&  sequence() const;
    Position position() const;            // locate() at the current playhead
    uint32_t sequenceRevision() const;    // changes whenever the sequence changes
};

What advance does

The domain has no clock. Time only moves when the engine says so. The engine renders audio in pieces: it asks position() what to play, renders that many frames, then calls advance with the time it just rendered, converted to beats. advance moves the playhead forward by that amount and wraps it to 0 when it passes the end of the loop. It returns how many times the loop wrapped during that step (in practice 0 or 1). The web flavor uses that number to count loops for Randomize Every (§9). When playback is stopped, advance does nothing and returns 0.

Playhead in beats. The concept stores t in seconds and scales it by oldBPM / newBPM on a BPM change (§10). Storing t in beats gives the same result with no scaling step. Seconds are derived as tBeats × beatSec where the formulas need them.

8. Core engine interfaces

SampleBuffer

One track's audio data, already converted to the output sample rate. It never changes after creation and is owned by the host, not the engine.

struct SampleBuffer {
    const float* channels[2];         // mono files point both channels at the same data
    int64_t frames;
    double  durationSec;              // original duration, used for TrackInfo
};

SampleBank

Lets the engine find a track's audio data by id. It stores pointers only.

class SampleBank {
public:
    void put(TrackId, const SampleBuffer*);
    const SampleBuffer* take(TrackId);        // removes and returns the pointer so the owner can free it
    const SampleBuffer* get(TrackId) const;
};

Voice

Reads one source from one position, with a volume ramp. A crossfade is two voices ramping in opposite directions.

class Voice {
public:
    void start(const SampleBuffer*, double readFrame, float fromGain, float toGain, int rampFrames);
    void fadeOut(int rampFrames);
    void render(float* l, float* r, int frames);   // adds into the output; silence past the end of the data
    bool active() const;
    const SampleBuffer* buffer() const;
    double readFrame() const;
};

Renderer

Decides when a crossfade is needed. At the start of every piece of audio it compares what should play with what is playing. If the track changed, sound changed to silence or back, or the read position jumped, it fades the old voice out and the new one in (§8.4). If the same track simply continues across a slot boundary, nothing changes. 

class Renderer {
public:
    void prepare(double sampleRate);
    void follow(const Position&, const SampleBuffer*, double slotSec);
    void render(float* l, float* r, int frames);
    void stopAll(int fadeFrames);
};

Engine

Owns the Session, the SampleBank and the Renderer. It is the core's single entry point for a host.

struct EngineEvents {                 // filled during one render call, read by the host afterwards
    int loopsWrapped;
    std::array<TrackId, 16> released; int releasedCount;   // buffers the host may now free
};

class Engine {
public:
    explicit Engine(uint64_t seed);
    void prepare(double sampleRate, int maxBlockFrames);

    void apply(const Command&);                    // includes RemoveTrackAt and MoveTrack
    void appendTrack(TrackId, const SampleBuffer*, double startPosition);
    void applyPreset(const PresetData&);

    void render(float* l, float* r, int frames);   // splits the block at slot boundaries and loop wraps

    const EngineEvents& events() const;
    void fillSnapshot(Snapshot&) const;
    PresetData presetData() const;
};
Engine behaviorDecision
Crossfade lengthThe shorter of 10 ms and the current slot (§8.4)
Crossfade shapeEqual-power. The sources are unrelated recordings, so a linear fade would sound about 3 dB quieter in the middle.
A switch during a fadeUp to three voices. The oldest fading voice is dropped when a third source arrives, which only happens with very small slices.
Start and stop10 ms fade-in when playback starts and 10 ms fade-out on stop. The concept doesn't cover this, but it removes the same click.

9. Platform flavors

The rules that differ between the products (§14.3) are still musical rules, so they live in the core. Each host creates only its own flavor. Nothing in the core asks which platform it runs on.

AutoRandomizer (web only, §9)

Counts completed loops and says when the sequence must be regenerated.

class AutoRandomizer {
public:
    void setEvery(int every);           // -1 = off
    void reset();                       // on Play and on manual Randomize
    bool onLoopWrapped();               // true when the sequence must regenerate now
    int  loopsRemaining() const;        // -1 when off
};

NoteTransport (VST only, §5.1)

Turns note and host events into Play and Stop according to the Playback Mode. Pitch and velocity are not passed in at all.

enum class TransportAction { None, Play, Stop };

class NoteTransport {
public:
    void setMode(PlaybackMode);
    TransportAction noteOn();                           // always Play (restart from t = 0)
    TransportAction noteOff();                          // Gate: Stop when no notes are held
    TransportAction hostPlayingChanged(bool playing);   // host stopped → Stop
    TransportAction pending();                          // Stop after switching Trigger → Gate with no notes held
    void reset();
};

WebEngine

An Engine plus an AutoRandomizer. Play and Randomize also reset the loop counter; loop wraps reported by the engine drive automatic regeneration.

class WebEngine {
public:
    explicit WebEngine(uint64_t seed);
    void prepare(double sampleRate, int maxBlockFrames);
    void apply(const Command&);
    void appendTrack(TrackId, const SampleBuffer*, double startPosition);
    void applyPreset(const PresetData&);
    void render(float* l, float* r, int frames);
    void fillSnapshot(Snapshot&) const;            // includes loopsRemaining
    const EngineEvents& events() const;
};

VstEngine

An Engine plus a NoteTransport. Notes carry their position inside the block so playback starts on the exact frame.

class VstEngine {

10. Command and Snapshot contract

Plain, fixed-size data with no pointers, so it can cross any channel in section 5 unchanged.

struct Command {
    enum class Type : uint8_t {
        Play, Stop, Randomize,
        SetBpm, SetLoopSize, SetSliceSize, SetRandomizeEvery, SetPlaybackMode,
        SetStartPosition,   // a = index, value = position
        RemoveTrackAt,      // a = index
        MoveTrack           // a = from, b = to
    };
    Type    type;
    double  value;          // bpm, start position
    int32_t a;              // loop size, slice exponent, randomize every, mode, index, from
    int32_t b;              // to
};

struct Snapshot {
    // settings
    Settings settings;
    int      validSliceMin, validSliceMax;     // slice exponents the UI may offer (§3.1)
    // transport
    bool     playing;
    double   tBeats;
    int      currentSlot;                      // -1 = remainder or stopped
    int      loopsRemaining;                   // web only, -1 otherwise
    int      heldNotes;                        // VST only
    // tracks, in list order
    int      trackCount;
    struct Track { TrackId id; double startPosition; double durationSec; int sliceCount; };
    std::array<Track, TrackList::kMaxTracks> tracks;
    // sequence (effective indices after remap; -1 = silence)
    uint32_t sequenceRevision;
    int      slotCount;
    std::array<int16_t, Sequence::kMaxSlots> effective;
};

Appending a track and applying a preset are not commands: the first carries audio data and the second carries variable-length text, so each host has its own call for them (VstBridge, EngineClient).

Track names are not in the snapshot, because names come from files and the core doesn't know about files. Each host keeps a TrackId → name map, and the presenter joins it with the snapshot rows.

11. Presentation: view models and presenters

Both platforms use the same pattern. The on-screen controls belong to the view model and are specified in a separate document; this section only fixes how the view model and the presenter meet. 

 view model ── randomizePressed ──▶ presenter ── Command ──▶ host
 view model ◀── loopSize.set(12) ── presenter ◀── Snapshot ── host
  • View model holds properties (values the screen shows) and actions (one public method per user gesture: a press, a value change, a drag). An action method does nothing except fire a signal. A property's set notifies listeners only if the value actually changed. The controls read the properties and call the actions. They never see the presenter or the host.
  • Presenter is the only active part. On construction it connects to every action signal of the view model and forwards each one to the host as a command or host call. When a new snapshot arrives, it converts it into display values and calls set on the matching properties.

The presenter can be checked without any screen, and the musical rules stay in the core. The view model and presenter are separate per platform, because the controls differ and a shared base would tie the two UIs together.

12. VST host interfaces

BeatalityProcessor

The plugin object the DAW talks to. Its audio callback does all the real-time work in a fixed order: apply pending commands, pass the DAW's play state and the MIDI notes to the VstEngine, render, publish a snapshot, and hand back any released buffers. Its part of the DAW project contains only the parameters, in the same text format as a preset. Samples are not saved with the project. No parameters are exposed to the DAW for automation. 

class BeatalityProcessor {
public:
    BeatalityProcessor();                              // stereo out, MIDI in, no audio in

    void prepareToPlay(double sampleRate, int maxBlock);   // converts tracks again if the rate changed
    void releaseResources();
    void processBlock(AudioBuffer&, MidiBuffer&);

    void getStateInformation(MemoryBlock&);            // encodePreset(engine.presetData())
    void setStateInformation(const void* data, int size); // decodePreset → applied like a loaded preset

    VstBridge& bridge();
    virtual Editor* createEditor();                    // overridden by the app layer
};

VstBridge

The host's API for the presenter. Every method runs on the UI thread and returns immediately; results show up in a later snapshot or through onError.

class VstBridge {
public:
    void send(const Command&);                         // includes RemoveTrackAt and MoveTrack
    bool latest(Snapshot& out);                        // true if newer than the last read
    std::string trackName(TrackId) const;

    void appendFiles(const std::vector<std::filesystem::path>&);   // loaded in the background, appended in order

    void savePreset(const std::filesystem::path&);
    void loadPreset(const std::filesystem::path&);
    std::function<void(std::string)> onError;
};

SampleLoader

Decodes a WAV or MP3 file and converts it to the plugin's output sample rate on a background thread, so the UI and the audio never wait for a file. Any other file, including an Ableton Live Clip (.alc), is rejected. When it finishes, it reports either the ready audio data or an error. 

class SampleLoader {
public:
    void load(const std::filesystem::path&, TrackId, double targetSampleRate);
    std::function<void(TrackId, LoadedSample)> onLoaded;
    std::function<void(TrackId, std::string)>  onFailed;
};

TrackStore

Owns every loaded track's audio data and display name. It gives the engine a pointer, and it frees the data only after the engine reports the track as released. When the DAW changes the sample rate, it has every track converted again. 

class TrackStore {
public:
    TrackId reserveId();
    const SampleBuffer* adopt(TrackId, LoadedSample, std::string name);
    void release(TrackId);                             // after the engine has let go
    std::string name(TrackId) const;
    void reconvertAll(double sampleRate);
};

CommandQueue and SnapshotBuffer

Move data between the UI thread and the audio thread without either side ever waiting. The command queue keeps every command in order. The snapshot buffer keeps only the newest snapshot, because the UI only ever needs the current state. 

template <typename T, int Capacity>
class CommandQueue {
public:
    bool push(const T&);                               // UI thread
    bool pop(T&);                                      // audio thread
};

template <typename T>
class SnapshotBuffer {
public:
    void write(const T&);                              // audio thread
    bool read(T&);                                     // UI thread; true if newer
};

PresetStore

Saves the current settings as a preset file on disk and reads one back (§11.2). The text itself comes from and goes to PresetCodec; this element only deals with files and folders.

class PresetStore {
public:

13. Web host interfaces

In the browser, the core runs on the browser's audio thread. The page's main thread, where the presenter lives, can only talk to it by sending messages. That gives the web host three parts: the engine boundary, the audio thread host, and the main-thread client.

13.1 Engine boundary

Browsers can't run C++ directly. The core is compiled to WebAssembly, a compact binary format that browsers execute at close to native speed. Browser code can only call functions that the compiled module exports, and those functions can only take and return numbers. Anything larger, like audio data, preset text or a snapshot, lives in the module's memory, and the two sides exchange its address. So the core can't be used from the browser as C++ classes. It needs a flat list of plain functions that wrap WebEngine. That list is the engine boundary (often called an ABI, application binary interface). 

extern "C" {
    Handle create(uint32_t seedLo, uint32_t seedHi, double sampleRate, int maxBlock);
    void   destroy(Handle);

    void   command(Handle, int type, double value, int32_t a, int32_t b);
    char*  textAlloc(Handle, int length);                     // caller copies preset text into this memory
    bool   applyPresetText(Handle, const char* text, int length);   // decodePreset + applyPreset

    float* trackAlloc(Handle, uint32_t id, int64_t frames, int channels);    // caller copies audio into this memory
    void   trackAppend(Handle, uint32_t id, double durationSec, double startPosition);

    float* output(Handle, int channel);                       // where render() writes
    void   render(Handle, int frames);
    const Snapshot* snapshot(Handle);                         // read field by field from module memory
}

13.2 AudioThreadHost

Browsers let a page run its own code on the audio thread by registering an audio processor class. The browser calls that class every 128 frames (about 3 ms) and expects audio back. AudioThreadHost is Beatality's processor. It loads the compiled core, applies incoming messages through the engine boundary, calls render on every call from the browser, copies the output to the speakers, and posts a snapshot back to the page about 30 times a second. It is the web counterpart of BeatalityProcessor.

14. Data formats

14.1 Preset

A small text file in JSON format, so it can be written by hand and served as-is from the website. Encoded and decoded only by PresetCodec.

{
  "format": "beatality-preset",
  "version": 1,
  "name": "Choppy breaks",
  "bpm": 120,
  "loopSize": 8,
  "sliceSize": "1/4",            // one of 1/64 … 16
  "randomizeEvery": 2,           // -1 or 1..8
  "playbackMode": "gate",        // "trigger" | "gate"
  "startPositions": [0, 0.5, 0.25]
}

Unknown fields are ignored. A file with a higher version is rejected.

14.2 VST project state

The plugin's part of a DAW project is the same preset text. No samples, file paths or sequence are stored. After a project opens, the plugin has its parameters back and an empty track list.

15. Decisions

  • Sequence storage: the sequence is never stored, in presets or in DAW projects.
  • Track list operations: append, remove at index, move from one index to another. A move does not change the sequence and the sequence is not told about it. A slot keeps its index.
  • DAW automation: no parameters are exposed to the DAW.
  • DAW project contents: parameters only, in preset format. Samples are added again by the user.
  • File formats: WAV and MP3 on both platforms. An Ableton Live Clip (.alc) is a clip description that points at a sample; it is not audio, and it is rejected.
  • Randomness: each instance starts from an unpredictable seed taken from the operating system or browser. The seed is not shown to the user.
  • First plugin target: VST3.
  • Web snapshot channel: messages about 30 times a second, which work on any website. This is enough for a demonstration widget; shared memory is the fallback if the display turns out to lag.
  • Plugin licence: the plugin is sold closed-source. JUCE is used under its free Starter licence, which allows closed-source commercial products while revenue from the product stays under $20,000 per year. Above that, an Indie licence is required (see 16.3).

16. Tech stack

This section ties each layer to a concrete technology and explains the choice.

16.1 Core domain and core engine: C++20

The core has to run inside a VST plugin, where C++ is the standard language, and inside a web page. C++ covers both: it compiles natively for the plugin, and the same source compiles to WebAssembly for the browser (section 13.1). Writing the core once is the only reliable way to guarantee that both products behave identically. A second implementation in another language would slowly drift apart from the first.

C++20 specifically brings std::span (views over arrays without copying), std::optional (for "silence" and "no track" results), and designated initializers for readable settings structs. The core uses only the standard library, with no third-party dependencies, so it builds the same way for both targets. PresetCodec uses a small hand-written reader and writer limited to the preset format, rather than a general JSON library. Floating-point "fast math" compiler options stay off, so the native and web builds compute identical numbers.

16.2 Build: CMake

CMake is the build system that both the plugin framework and the WebAssembly compiler support directly, so one build description produces the core library, the plugin and the web module. Named build presets (for example plugin debug, plugin release, web release) keep the command lines out of people's heads. The compiler for the plugin is MSVC 2022 on Windows.

16.3 VST host, VST view model, presenter and views: JUCE 8

JUCE is the most widely used C++ framework for audio plugins. It provides the pieces the VST host needs: the VST3 wrapper, the audio callback, MIDI input, the DAW's play state, project save and recall, audio file decoders, file dialogs, and a lock-free FIFO used for the command queue. It also has its own UI toolkit, which the VST views use, including a skinning system suited to the Winamp look.

JUCE is used only in the VST column of the layers. The core never includes it.

Licence. JUCE is offered either under AGPLv3, which would force the plugin's source to be published, or under its own commercial licence. Beatality is sold closed-source, so it uses the commercial licence's free Starter tier. Starter allows closed-source commercial distribution with no splash screen, as long as the revenue generated by the product (sales, donations, sponsorship) stays under $20,000 over the previous 12 months. Above that, the next tier is Indie (up to $300,000; $40 per month or $800 perpetual at the time of writing). The terms are in the JUCE 8 licence; check the current terms before release, because a newer major version may change them.

The VST3 SDK itself is MIT-licensed, so selling a VST3 plugin needs no extra fee. Using the "VST" name or logo on the product page needs Steinberg's separate (free) usage agreement.

16.4 Sample-rate conversion in the plugin: r8brain-free-src

A sample recorded at 44.1 kHz must play at the correct pitch in a 48 kHz project (§13). The plugin converts each sample once, at load time, rather than during playback. r8brain-free-src is a small, high-quality converter under the MIT licence that is common in commercial audio software. Converting at load time keeps the audio thread simple and cheap.

16.5 Web engine: WebAssembly via Emscripten

Emscripten is the standard compiler from C++ to WebAssembly. It produces one small binary module containing the core. The build exports only the engine boundary functions, and leaves out the file system emulation and exceptions, which keeps the module small and lets it load on the browser's audio thread.

16.6 Web audio: Web Audio API with an AudioWorklet

The Web Audio API is the browser's built-in audio system, supported by every current browser. Its AudioWorklet feature is the mechanism behind AudioThreadHost: the page registers a processor class, and the browser runs it on its real-time audio thread. Older approaches ran audio code on the page's main thread, where any UI work causes dropouts. The same API's decodeAudioData decodes WAV and MP3 uploads and converts their sample rate, so the web host needs no decoder of its own.

16.7 Web host client, view model and presenter: TypeScript

The page side of the web host, the web view model and the web presenter are written in TypeScript, which is JavaScript with type checking. The Command, Snapshot and view model types in this document are mirrored as TypeScript types, so a mismatch with the core shows up when compiling, not as a silent bug in the browser. Where this document shows C++ signatures for these elements, the TypeScript versions use promises instead of callbacks, and the browser's own types for files and the audio context. Property and Signal map onto Preact signals (16.8).

16.8 Web views: Preact with signals

Preact is a very small (about 4 KB) library with the same component model as React. Size matters because the widget is embedded in someone else's page. Its "signals" feature updates only the parts of the screen whose data changed, which fits a view model whose playhead changes 30 times a second while everything else is mostly still.

16.9 Embedding: a custom HTML element

The widget app is packaged as a custom HTML element, <beatality-player>. The website adds one tag and one script. The element keeps its markup and styles in a Shadow DOM, an isolated area of the page, so the website's CSS can't break the widget's look and the widget's CSS can't leak out.

16.10 Web build: Vite and pnpm

Vite bundles the TypeScript and views into one script, alongside the audio thread file and the WebAssembly module, and provides a fast development server with live reload. pnpm manages the web packages and lets the web host, view model, presenter and app live as separate packages in one repository, matching the layer folders.
